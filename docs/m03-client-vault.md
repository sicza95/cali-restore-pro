# M-03: local vault and device recovery

This milestone builds on rebased and merged [M-02 PR #7](https://github.com/sicza95/cali-restore-pro/pull/7) at 5a965b2 on feat/storybook-foundations. It handles synthetic records only. Account authentication authorizes entry to the controls; it never derives a content key. The browser has no vault upload endpoint. M-04 owns chunked file storage and M-06 owns online sharing.

## Threat and format contract

Protect content against a copied ciphertext store or backup, a wrong recovery key, altered or swapped envelopes, and accidental access by another account. This does not protect an unlocked browser, same-origin script injection, a compromised OS/browser, or an operator serving malicious client code. A remembered browser profile contains a usable origin-bound key handle; do not opt in on shared devices. An offline browser cannot establish account revocation or detect rollback to an older valid backup. Origin storage can be cleared or evicted. No idle timer. No guarantee of memory erasure, physical disk erasure, or remote recall.

Use the browser's [Web Cryptography API](https://www.w3.org/TR/webcrypto/) and [IndexedDB](https://www.w3.org/TR/IndexedDB/), with no new crypto dependency. A recovery key is 32 random bytes (64 hexadecimal digits); its imported HKDF handle is nonextractable. Each seal derives an AES-256-GCM key via HKDF-SHA-256 with a fresh 32-byte random salt and the context bytes as info. Use a fixed all-zero 12-byte IV under that single-use derived key and a 128-bit tag. Uniqueness depends on the platform CSPRNG; with 256-bit salts, collisions under the same root and context are negligible. Authenticate before decoding UTF-8/JSON.

Envelope v1 is JSON with exactly the writer fields `version` (1), `salt` and `ciphertext` (standard padded Base64 for bytes, ciphertext followed by tag). Context for HKDF info and GCM additional data is UTF-8 JSON serialization of ["calirestore-vault",1,accountId,purpose]; purpose is "snapshot" or "transfer". v1 holds one bounded synthetic text snapshot per account. A separate random 32-byte hex stamp is the compare-and-swap revision for local writes and trust changes; the ciphertext, key handle (if opted in) and stamp commit together in an IndexedDB strict read-write transaction. No reuse of a previous salt on retry. A recovery file is the committed snapshot envelope; it contains no key. The account ID is supplied independently by sign-in. A fresh browser restores by supplying that file and its recovery key. Restore never overwrites an existing vault. A session-only browser needs its recovery key again after lock/reload.

Device approval is local and out of band. The receiving browser creates a random pairing code in memory. Compare or pass it directly to the unlocked source device, which exports a transfer file encrypted to that code and account. The receiving browser authenticates the file, consumes its in-memory code, and provisions an independent local vault and recovery key. A copied pairing code plus transfer file can be used by anyone possessing both; no server revocation, expiry ledger, or online identity is implied. Transfer is a copy at a point in time, not sync. Keep files and keys separately. Forget requires explicit discard authorization and atomically deletes the local row; an unverified export never bypasses the confirmation.

## Future sharing design and release gate

M-06 must bind an authenticated stable recipient public key to the verified immutable account ID, pin its fingerprint in encrypted owner state, and suspend new grants on identity change until explicitly reviewed. Use established [HPKE (RFC 9180)](https://www.rfc-editor.org/rfc/rfc9180.html) with a vetted implementation selected and reviewed before rollout. Authenticate envelope sender/recipient binding, project, grant, scope, epoch and format version. Separate independent keys for assessment, published summary, full estimate and personal library; selected historical checkpoints need independent keys and dependency closures so granting one does not grant other history. Rotate only affected scope epochs after read revocation; current writes pause until the new key set commits. Previously delivered keys cannot be recalled. M-07 owns the policy and persistence for locked unsynced recovery drafts and restore watermarks. Local vault roots are not recipient identities or project keys. No production content or collaborative deployment before the independent cryptographic review. Passkey compatibility stays a separate gate.

## Metadata and logs

No new server fields or API calls for vault actions. The browser persists account ID, version, random salt, ciphertext length/bytes, local revision stamp and optional origin key handle. No plaintext notes, names, photos, masks, dimensions, credentials, recovery codes or raw keys in storage, logs, telemetry, URLs or server backups. Security preferences and sign-in metadata predate the vault.

Server storage allowlist: see migrations 0001–0004 for the exact schema: migration version/checksum/time; account UUID, email, password verifier, state/role, language, entitlement/delegation/quota and creation time; bootstrap guard singleton/account/count; session ID, account ID, token digest and creation/verification times; keyed rate bucket, window and count; audit ID, actor/subject, enumerated action and time; identity link digest, account, purpose, target email and expiry; outbox ID, sealed mail payload, status, attempt count and timestamps. No general-purpose metadata map.

Application stdout fields: time, level, fixed message, and boolean ready on worker readiness changes. No raw error strings, request URLs/queries, headers, bodies, IPs, key material, or user-agent logging. Production ingress must disable access logs and body capture; database infrastructure must disable statement/parameter capture; retain sanitized operational stdout at most seven days. Existing identity audit and mail retention, ingress/database configuration verification and restore enforcement remain deployment/M-07/M-16 gates. Future sync may add only opaque IDs, explicit membership/scopes, public keys and sealed envelopes, schema/revision/epochs, byte counts and timestamps via an updated allowlist.

## Verification

Use synthetic inputs only. Browser checks must cover wrong key, altered ciphertext, fresh browser recovery and approval, remembered versus session-only lock, cross-account rejection, conflicting/interrupted writes and deliberate forget. Physical Safari/iPad and independent cryptographic review are separate.

The fixed v1 vector in tests-platform/fixtures/vault-v1.json uses account 10000000-0000-4000-8000-000000000001, a root of 32 bytes of 0x01, a salt of 32 bytes of 0x02 and JSON text "vault vector v1". Node crypto hkdfSync and createCipheriv produced the fixture independently of the browser Web Crypto implementation. The browser opens it through the normal recovery UI.

The browser suite uses real Web Crypto, IndexedDB, downloads, separate browser contexts and same-origin tabs. Only account API responses are fixtures. It injects an IndexedDB abort after the put succeeds but before commit, and confirms the previous snapshot survives a reload. A separate test rejects a stale tab write. The Go log test feeds private diagnostic text to the HTTP logger and verifies that only the three allowed event fields are emitted.

Layout evidence from Chromium: [iPad landscape, unlocked](evidence/m03/vault-landscape.png) and [iPad portrait, locked](evidence/m03/vault-portrait.png). The vault follows the existing Account Security section and theme, with separate controls for local unlock, backup and account sign-in.

Executed locally: npm check, production and Storybook builds, 11 Storybook browser tests against the built output, five vault and two settings browser tests, and go test ./... using the existing test image with networking disabled. Database-dependent integration coverage remains in CI.
