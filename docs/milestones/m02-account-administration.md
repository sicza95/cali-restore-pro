# M-02 account settings and administration

M-02 builds on rebased and merged PR #6 at `7767f39` on `feat/storybook-foundations`. Review: M-02 PR #7.

## Settings and administrative controls

- `/settings/account` shows the signed-in address, links to credential management, and checks deletion eligibility. `/settings/security` retains credential changes and session controls. The user and superuser deletion checks both return `project_continuity_unavailable`. There is no destructive route.
- `/settings/preferences` saves account-specific preferences in the current browser. Theme and transparency apply to the shell. Area units, currency, drawing, independent report language, and branding (including a small PNG logo) are defaults for future project and reporting features. Branding remains on the device. Optional diagnostic consent defaults off; no reporting collector or upload is enabled.
- `/admin` shows server capability scoped controls. Account search matches literal case insensitive email prefixes and returns at most 20 rows plus a cursor. Administrators with lifecycle or entitlement permissions see ordinary members only. Operations-only administrators see mail and audit status without access to account search.
- Platform roles never confer feature entitlements, project membership, or access to content keys. Feature access is explicit and defaults off. Quotas are whole MiB, from 0 to 1,048,576, with zero allocating no capacity. These fields are ready for the project storage milestone; no current usage or project transfer is reported.
- Superusers manage roles and can delegate lifecycle, feature/quota, and operational visibility independently. Existing administrators retain their previous lifecycle authority when migrated. Newly promoted administrators start with no delegated rights. Role or delegation changes revoke the subject's sessions and outstanding account links in the same transaction. Suspension keeps the account and revokes access; re-enabling does not revive revoked sessions.
- Admin mutations require the normal CSRF checks, a deliberate confirmation and credential verification within five minutes. Server authorization runs inside the identity mutation transaction. The database still protects the final active superuser.
- Operations shows mail counts, the latest 20 job statuses, and the latest 25 security events. Job metadata is limited to opaque ID, mail kind, creation time, status and attempts. Audit metadata includes opaque actor/subject IDs, their current account emails (null for deleted accounts), time and action. Mail recipients, payloads, failure strings, project data, secrets and credential material are excluded. Only active sessions with `operations.view` may read this metadata; account search permission is independent. The existing worker handles retries. Terminal mail metadata uses the existing seven-day cleanup; audit retention and restore qualification remain future work.

Device trust, local unlock and recovery start in M-03. Ownership/hosting transfer, usage accounting, and deletion safeguards depend on M-05 through M-07. Project report overrides and diagnostics transmission require their own integration and verification.

## Readable operational references (#77)

Mail jobs show a localized mail kind, status, time, attempts and an eight-character reference. Security events retain their localized action and show current actor/account emails alongside short references, falling back to the localized role label when an account is gone. Each reference is a 44 px copy button: it copies the complete ID, exposes it in the title, and reports success or failure in EN/HU. No email lookup depends on the account search page or on account-view permission.

Follow-up #111 adds required nullable `actorEmail` and `subjectEmail` fields to audit rows and a required `kind` field to job rows in `GET /api/v1/admin/operations`. Migration 0024 stores only the mail purpose (`verify`, `reset`, `email`, `security`, `project-invitation`) alongside the sealed payload when enqueued. The kind survives terminal payload erasure. Existing jobs keep an empty kind and the localized Mail job fallback; no historical payload is decrypted or backfilled. Emails reflect the current accounts, not historical addresses or mail recipients. The existing transactional session and `operations.view` checks run before any metadata query. PostgreSQL HTTP tests cover these fields, deleted actor/subject fallbacks, all mail kinds after payload erasure, operations-only access, denied member/delegated/suspended/anonymous sessions and revoked access.

Synthetic browser evidence: `admin-layout.browser.ts` covers filled and empty pages in EN/HU, light/dark and both iPad orientations, including expanded mail jobs, copy guards, axe and touch targets. `admin-references.browser.ts` checks every displayed reference/title and copying full mail, actor and subject IDs, plus denied clipboard feedback. These are mocked API and clipboard checks, not live mail delivery or physical iPad qualification.
