# M-07 project and account lifecycle

Hosted project owners can move a project to server trash, recover it, or explicitly queue early live purge. The trash view shows the server's recovery deadline and the upper bound on backup expiry. Trash counts against the current host's quota until its file and revision rows are purged. Recovery checks current ownership and, when a host is assigned, its active state, hosting entitlement and quota. Local copies and user-exported encrypted archives remain under the user's control.

Voluntary account deletion requires recent password confirmation, confirmation that pending work has been resolved, and a server continuity preflight. Transfer any surviving hosting to an eligible co-owner through the existing offer and acceptance flow. Sole owners can first complete a co-owner grant and hosting transfer or explicitly delete the project and let its live purge complete. Deletion removes the departing owner's membership and incoming grants, revokes sessions and links, and preserves surviving projects and completed transfers. A superuser can request deletion of another account after the continuity preflight passes. A superuser can explicitly force deletion of another account when that preflight reports unresolved project dependencies. Both paths require recent password confirmation and protect the final active superuser.

Forced deletion removes the departing account from co-owned projects and leaves surviving owners and their grants in place. If the departing account was the host, the project has no host until an eligible existing owner explicitly takes over hosting in the project owners panel. The existing quota check applies to the full project charge, and pending uploads from the departing host are cancelled. Hosted file and revision writes resume after hosting is claimed, subject to the existing epoch and rotation checks.

Sole-owner projects enter a read-only recovery window. Existing active grants permit only their already authorized ciphertext, originals, scopes and checkpoints until the deadline. Grant acceptance, activation and project writes are blocked during the window. Previously trashed projects stay in trash. Early account purge also ends the sole-owner project windows. The worker purges those projects before removing the account record.

Password-based recovery reinstates the account's previous active or suspended state and requires fresh sign-in. It lifts sole-owner freezes created by forced deletion so a recovered active owner can arrange a normal handover. It preserves existing trash and does not rejoin co-owned projects, restore incoming grants or reclaim hosting.

Deletion and recovery use a PostgreSQL clock with 720 hours of live recovery and an upper backup deadline of 2,160 hours from the original deletion action. Early purge closes recovery immediately. The worker removes live object directories before committing the project purge, so an interrupted purge can retry. UUID-only purged records survive removal of the live rows. Surviving grants can retain a sender's public sharing key until their last reference is removed.

## Operational object archives

Run the commands below from the deployed Compose project after applying migrations and starting the app and worker. The managed archive volume serializes backup and restore with an operation directory. After a process interruption, confirm that its containers and streams have stopped and inspect both database gates before removing the stale .operation directory. Ensure the current PostgreSQL authority is available and protected by deployment-level synchronous replication or equivalent current-state continuity. Keep the database, archive-key table and archive volume under operator control.

```sh
node scripts/operational-backup.mjs backup
node scripts/operational-backup.mjs restore ARCHIVE_ID FRESH_COMPOSE_PROJECT
```

The backup quiesces app and worker and saves committed encrypted objects to the managed archive volume, wrapped with a fresh AES-256-GCM key held in PostgreSQL. Each archive is readable for 60 days from the beginning of capture. Archive creation excludes live trash whose recovery deadline has already passed. The latest capture that can include deleted data is therefore within its first 30 days, yielding at most 90 days total. The worker deletes expired keys and files and retries cleanup on restart. If the worker is offline at the deadline, the restore command rejects expired keys immediately and physical cleanup resumes on restart. Snapshots, replicas and exports of the managed volume or key table require the same expiry policy. Historical database or WAL retention must be configured separately before production qualification.

Restore uses the current PostgreSQL database as the authority for policy, identities, deletion records, hosting and committed file metadata. It selects only currently referenced eligible objects from the older ciphertext, clones current state with empty sessions, links, mail and archive keys, processes due purges, discards staged metadata and checks every current committed part by size and SHA-256. Missing or corrupt current content stops the restore with the target gated. Historical bytes without current metadata are removed. Use an archive that contains the currently referenced committed objects. Loss of the current PostgreSQL authority requires a separate current-state recovery mechanism. The legacy substrate restore accepts only empty identity databases.

Successful verification fences the previous authority before opening the target gate. The old worker continues archive retention only. After review, start the new app and worker and create fresh backups there. If interrupted after fencing and before opening the target gate, keep both sides closed until the operator identifies the authoritative database. A failed target can be discarded and retried under a fresh Compose name once authority is established. Never reset the retired-source fence after the target has accepted traffic.

Retire the old database and object volumes after the target accepts traffic. Treat retained source volumes as a historical copy and apply a maximum 60-day retention measured from fencing, subject to any earlier deadline for already-deleted content. The Compose worker owns managed archives. Infrastructure lifecycle policy owns retired database and object volumes, WAL, replicas and off-host copies.

## Production retention verification

Record these checks against the actual production authority and backup destinations. The checked-in Compose file and disposable restore drill cover the application-managed archive path. Production WAL, retired volumes and off-host copies have separate retention controls.

| Copy            | Evidence to capture                                                                                                                                                                                                                                                                                                                                                              |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL WAL  | Read `pg_settings` for `archive_mode`, `wal_keep_size` and `max_slot_wal_keep_size`. Check live slot and archive lag, the oldest recoverable timestamp, and the expiry rule and observed expiry at the actual archive destination. Include replica slots and base backups that still contain the affected rows or archive keys. Size limits alone do not prove age-based expiry. |
| Retired volumes | Match each retired database and object volume, including snapshots, to its recorded source fence time. Verify deletion by 60 days from fencing or the earliest applicable deletion deadline, whichever comes first. Check the volume inventory after that deadline.                                                                                                              |
| Off-host copies | Inventory destinations for objects, database and WAL backups, archive keys, snapshots and replicas. Verify lifecycle rules and observed removal for each destination, including older object versions and retained snapshots. If no copies exist, record the provider inventories and replication configuration that establish this.                                             |

Each check must show that deleted content and keys needed to recover it expire within 90 days of deletion.
