# Draft source on the project page

16 November 2026 · Status: in progress · Issue: #72 · Found while doing [the photo removal with drafts](removal-drafts.md) (#67)

Goal: the project page blocks removing or re-roling the photo the drawing drafts belong to while they are pending, as the surface page does, so the drafts cannot be dropped silently.

## Where things stand

On `main` at `e7e92af`, the surface page passes `pendingSource` to `ProjectOriginals` (`SurfaceWorkspace.tsx`: `recovery.journal()?.drafts.length ? reference()?.id : undefined`). `ProjectOriginals` then disables that photo's "Remove" and its role select; "Remove" carries the `draftPhoto` reason as its `title` ("Resolve the drawing drafts before changing this original."), the role select has no reason. The project page (`ProjectDetail.tsx`) renders `ProjectOriginals` without `pendingSource`. Removing the photo there drops its whole assessment (`updateSurfaceImages` keeps only assessments whose source is attached), and its journal stays in storage with nothing that reads it. Changing its role to reference hides the drafts, since the surface page opens the journal of the first mapping photo only.

## Findings

- **What "pending" means on the surface page.** `recovery.journal()?.drafts.length`: the journal's `drafts` list is not empty. A draft is a layer with `pending` and `undone` marks, and undoing every pending mark keeps the draft with `undone` marks only (`setDraft`), so undone drafts count. A conflict keeps the drafts too (`openJournal`, `currentJournal`), so it counts. Only committing or discarding a layer's draft (or discarding a conflict) removes it. The journal's head plays no part, so the stored text alone answers the question: "does this journal have drafts" is `parseJournal(text).drafts.length > 0`. While the journal loads or when it fails to load, the surface page blocks nothing.
- **The draft source.** The surface page opens one journal: that of its reference, the first photo with the mapping role (`reference()`). The project page uses the same photo of the selected surface and reads its journal.
- **More than one assessment with drafts.** A surface can hold several assessments (one per photo that was the reference), each with its own journal, so in storage more than one can hold drafts. Only the current reference's drafts are reachable, on the surface page as well. Others arise when the reference changes while drafts are pending: until now through the project page (this issue), from another device's revision, and on both pages by giving the mapping role to a photo listed before the reference (only the reference itself is blocked). The hidden drafts come back when the roles are changed back, but the old reference is then an ordinary photo and can be removed, which drops them. That path exists on the surface page too, so it is not fixed here: recorded as #75. Blocking every photo whose journal holds drafts would be wrong: a hidden source's role select would then be blocked too, and the drafts could never be brought back.
- **Same-session freshness.** The project page and the surface page are different routes of `ProjectWorkspace`'s `Switch`, so `ProjectDetail` mounts again on the way back from the surface page and reads the journal again. Within the page, the read is keyed on the project, the selected surface, its draft source photo and the project revision, so it runs again when the selected object or surface changes, after every save and after a sync resolution replaces the project. Nothing on the project page writes drafts; a detail removal carries them unchanged (#67).
- **Other project-page actions.** There are no controls to delete an object or a surface. Archiving hides the surface and keeps the project and its journals; restoring it shows them again. Deleting the project ("Delete project", hosted trash) is an explicit, confirmed deletion of the whole project, not a silent loss. Restoring a backup creates a new project with new photo ids and leaves the existing project and its journals as they are; backups do not include journals by design ("Unfinished drafts and recent history reopen on this device"). "Keep cloud" in sync replaces the project row and leaves the journal, which then reports a conflict (#67). None of these orphans drafts the way this issue does.

## Approach

1. **Platform.** In `surface-journal.ts`, `hasDrafts(journal)` (the rule) and `storedDrafts(text)` (the rule on a stored journal). In `surface-attachments.ts`, `draftSource(readJournal, scope, surface)` returns the first mapping photo's id when its journal has drafts. The surface page uses `hasDrafts` for its `pendingSource`, so both pages share one rule.
2. **Project page.** `ProjectDetail` reads the draft source with a resource keyed as above and passes it to `ProjectOriginals` as `pendingSource`. While the read runs, the originals' controls are disabled as during a save, so no removal slips in before the answer. A failed read blocks nothing, as on the surface page.
3. **Reason.** The role select gets the same `draftPhoto` reason as "Remove", on both pages, so the disabled select explains itself (accessible description). No new text.
